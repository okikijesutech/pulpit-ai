# Architectural Decision Records (ADRs)

## ADR-001: Runtime Stack Selection (Electron + TypeScript + Native whisper.cpp)
* **Date:** 2026-11-01
* **Status:** Confirmed & Approved
* **Context:** Target hardware is an HP EliteBook 840 G3 (Intel Core i5-6300U, 2 cores / 4 threads, 8 GB RAM, 11.04 GB free SSD storage on Windows 10 Pro).
* **Decision:** Selected Option 2 (Electron desktop shell with native C++ `whisper.cpp` worker subprocesses and SQLite FTS5) over Option 1 (Python/FastAPI) and Option 3 (Rust/Tauri).
* **Rationale:**
  * Python + PyTorch requires 3–5 GB of disk space (which would exhaust the 11 GB available) and consumes 1 GB baseline RAM.
  * `whisper.cpp` compiled with AVX2 runs in < 200 MB disk space and 150–350 MB RAM for quantized models (`base.en-q5_1`).
  * Separate OS processes ensure fail-closed crash isolation.

## ADR-002: FreeShow State Observability and Authority Guard
* **Date:** 2026-11-01
* **Status:** Confirmed & Approved
* **Context:** FreeShow does not provide synchronous pre-event hooks to intercept manual operator clicks inside its GUI.
* **Decision:** Pulpit AI does not attempt to lock or hijack the FreeShow UI. Instead, the Central Authority Manager controls Pulpit AI's internal dispatch channel and revokes AI projection permissions instantly when manual activity or connection instability is detected.

## ADR-003: Public Domain and Verified Content Packaging
* **Date:** 2026-11-01
* **Status:** Confirmed & Approved
* **Context:** Modern Bible translations and contemporary worship lyrics are protected by copyright law and cannot be bundled in open-source distributions.
* **Decision:** Bundle the World English Bible (WEB) and King James Version (KJV) alongside pre-1928 public domain hymns. Provide an extensible `.pulpit-bible` and file import pipeline for local church licenses.

## ADR-004: Removal of Unsafe Presentation Defaults, Synthetic Timers, and Test Hooks
* **Date:** 2026-11-03
* **Status:** Confirmed & Approved
* **Context:** Initial prototypes used fallback default references (`John 3:16`, `43.3.16`), hardcoded authentication keys (`1445`), a 300ms synthetic timer falsely claiming command success, and development mocks that could leak into live audio inference or production builds.
* **Decision:**
  * Reject commands lacking an explicit, validated scripture reference (`success: false`). Never default to John 3:16 or any other verse.
  * Emit presentation commands exactly once per operator approval.
  * Require verified confirmation: directly via socket callback or by observing matching output events on FreeShow's broadcast channel. If unconfirmed after 1200ms, report fail-closed status `sent_unconfirmed`.
  * Read authentication credentials from operator configuration or detect them from local settings; never hardcode credentials.
  * Forbid automatic startup of `MockFreeShowServer` in production builds (`app.isPackaged || NODE_ENV === 'production'`). In dev, visibly display a persistent `SIMULATED` banner and `FreeShow: SIMULATED` status.
  * Restrict audio simulation test rigs behind development mode and clear mock registers immediately upon use to protect live microphone inference.
  * Disk space checks in `ModelManager` fail closed when filesystem stats throw errors.

## ADR-005: Candidate Approval by ID and Server-Side Registry (PR 3)
* **Date:** 2026-11-03
* **Status:** Confirmed & Approved
* **Context:** In early iterations, the renderer passed the entire suggestion payload object over IPC to `authority:approve-candidate`. A compromised renderer or forged IPC payload could submit arbitrary presentation actions and bypass AI verification. Furthermore, candidates lacked replay protection and lifetime bounds.
* **Decision:**
  * Candidates generated by AI engines are stored exclusively in the main process `CandidateRegistry` in `AuthorityManager`.
  * `authority:approve-candidate` strictly accepts a `candidateId: string`. Passing an object or un-registered ID is rejected fail-closed and logged as a security alert.
  * Suggestion approvals are strictly single-use; replay attempts are rejected.
  * Candidates carry an automatic 2-minute (120-second) expiry window.
  * Manual Lock active state unconditionally blocks approval of any candidate.

## ADR-006: Full Bible Data Acquisition and Cryptographic Fail-Closed Verification (PR 4)
* **Date:** 2026-11-03
* **Status:** Confirmed & Approved
* **Context:** Early prototypes embedded a small 55-verse TypeScript seed file (`SeedScriptureData.ts`). In production church use, this resulted in missing verses for legitimate sermon references outside the sample set. Furthermore, Scripture datasets required tamper-evident cryptographic verification to ensure biblical integrity.
* **Decision:**
  * Sourced the full 66-book Protestant Canon (1,189 chapters, 31,102 verses) from official eBible.org VPL datasets for both the World English Bible (WEB, 2020 Revision) and the King James Version (KJV, 1769 Oxford Standard Text).
  * Converted verses out of TypeScript code into versioned JSON data files (`web.json` and `kjv.json`) stored in `packages/scripture-engine/data/`.
  * Assigned authentic SHA-256 cryptographic checksums to each package metadata (`metadata.checksum` calculated over `JSON.stringify(verses)`).
  * Implemented fail-closed loading in `ScriptureDatabase`: during startup, package checksums are computed and compared against `metadata.checksum`. Any checksum mismatch or missing checksum immediately throws and refuses to register the translation or insert verses into storage.
  * Confirmed public domain licenses: WEB dedicated to Public Domain by Michael Paul Johnson; KJV 1769 Oxford Standard Text in Public Domain worldwide.
  * Reserved the 55-verse `SeedScriptureData.ts` exclusively for isolated, fast unit tests. All desktop startup and production workflows load the verified full Bible data files.

## ADR-007: Scripture Parser Guards, Cue Requirements, and Rolling Window Rules (PR 5)
* **Date:** 2026-11-04
* **Status:** Confirmed & Approved
* **Context:** In live preaching, colloquial speech patterns frequently collided with biblical book names and numbers (e.g., "mark 10 times" or "job 2 weeks ago" spuriously suggested Mark 10:1 or Job 2:1). Whole-chapter citations silently defaulted to verse 1 instead of presenting the chapter accurately. In multiline utterances, only the first reference was parsed. Additionally, subsequent conversational phrases (e.g. "Amen church", "Praise the Lord") caused the rolling window to re-parse and re-emit old references after the 10-second cooldown expired.
* **Decision:**
  * Require a structural or spoken cue for bare numbers (a colon `:`, `"chapter"`, `"verse"`, or explicit phrases such as `"turn to"`, `"open to"`, `"read from"`).
  * Cue-less matches receive lower confidence and a `needsReview: true` flag. Non-scriptural unit words (e.g. "times", "weeks", "days", "years", "percent") immediately reject matches.
  * Whole-chapter results are explicitly labeled as `"whole chapter, no verse given"` and retrieve all chapter verses, never silently defaulting non-Psalm books to verse 1.
  * `ScriptureReferenceParser.parseAll()` scans and returns all explicit references found within a segment.
  * Encapsulate rolling context window processing in `ScriptureCandidateGenerator.processUtterance()`. Re-parse the rolling window ONLY when the newest segment adds a book or number, preventing old references from re-triggering after cooldown expiry on conversational words.
  * When a rolling utterance refines a whole-chapter suggestion (e.g. "John chapter 3" followed by "verse 16"), the specific verse candidate supersedes the whole-chapter suggestion, ensuring a single final candidate.
